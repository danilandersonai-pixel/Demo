# DECISIONS — журнал решений проекта «Штурман»

Формат: дата · решение · почему.

## 2026-07-31 · Этап 0. Разведка

### Д-1. Источники данных: уровень A — транскрипты, уровень B — ФС + git

Разведка на этой машине (Linux, Node 22, git 2.43, Claude Code 2.1.220) показала:

- Транскрипты сессий лежат в `~/.claude/projects/<кодированный-путь-проекта>/*.jsonl`.
  Путь проекта кодируется заменой небуквенных символов на `-`
  (`/home/user/Demo` → `-home-user-Demo`).
- Формат — JSONL, по записи на строку. Типы записей, найденные в живой сессии:
  - `user` — сообщение человека **или** массив блоков `tool_result`
    (результаты инструментов возвращаются от имени user);
  - `assistant` — ответ Клода: массив блоков `thinking` / `text` / `tool_use`,
    плюс `message.model`, `message.stop_reason` и `message.usage`
    (input/output/cache-токены — источник для оценки расхода);
  - служебные: `queue-operation`, `attachment`, `last-prompt`, `summary`.
  - У содержательных записей есть `timestamp` (ISO), `sessionId`, `cwd`,
    `gitBranch`, `uuid`/`parentUuid`.

**Решение.** Уровень A — хвост самого свежего `.jsonl` проекта: из `tool_use`
и `tool_result` строится лента «что Клод делает», из `usage` — оценка токенов,
из затишья — детектор остановки. Уровень B — вотчер файловой системы + git;
включается автоматически, когда каталога транскриптов нет. Панель обязана быть
полезной и на B: карта проекта, git, лента файловых изменений работают без
транскриптов.

### Д-2. Хуки Claude Code: поддерживаются, но НЕ используем

На машине найдены рабочие хуки (`~/.claude/launcher-settings.json`:
SessionStart, Stop). Технически хук Stop — идеальный сигнал «Клод закончил».
Но чтобы «Штурман» получал хуки, пришлось бы **записать** их в настройки
Claude Code пользователя — а приложение по условию только наблюдает и ничего
не меняет. Детектор остановки строим на затишье в транскрипте +
`stop_reason` последней записи. Хуки упомянуты в README как опция для
продвинутых — вручную, по желанию пользователя.

### Д-3. Вотчер: свой на stdlib, chokidar — опционально

`fs.watch(..., {recursive: true})` не работает на Linux в Node 18 (появился в
Node 20), а по условию поддерживаем Node ≥ 18. Ставить chokidar обязательной
зависимостью — значит требовать `npm install` и сеть. Решение: собственный
рекурсивный вотчер — `fs.watch` на каждый каталог (это работает на всех ОС и
версиях), новые каталоги подхватываются на лету, события идут через дебаунс.
Если рядом установлен chokidar — используем его (`try { require('chokidar') }`),
нет — работаем сами. Итог: **нулевые обязательные зависимости**, запуск —
просто `node server.js`.

### Д-4. Поиск каталога транскриптов: кодирование пути + сканирование

Первично каталог ищется кодированием абсолютного пути проекта
(замена всего, кроме букв/цифр, на `-` — работает и для Windows-путей:
`C:\Users\x` → `C--Users-x`). Если каталога нет — fallback: сканируем
`~/.claude/projects/*`, читаем первые строки JSONL и сравниваем поле `cwd`
с наблюдаемым проектом. Если и это не дало результата — честно включаем
уровень B и говорим об этом в интерфейсе.

### Д-5. Активная сессия = самый свежий по mtime `.jsonl`

В каталоге проекта может лежать много сессий. Активной считаем ту, чей файл
менялся последним; если появился более свежий файл — переключаемся на него
на лету (Claude Code перезапустили — панель сама подхватит новую сессию).
Прошлые сессии доступны через журнал (`/api/sessions`).

### Д-6. Детектор «Клод остановился»

Два сигнала, оба из транскрипта:
1. **Явный**: последняя содержательная запись — `assistant` с
   `stop_reason: "end_turn"` (или текстовый блок без последующего `tool_use`) —
   Клод закончил ход и ждёт человека. Срабатывает после короткой паузы (5 с),
   чтобы не ложно срабатывать между записями.
2. **По затишью**: в транскрипте нет новых записей дольше порога (по умолчанию
   90 с) при живой сессии — «Клод давно молчит: возможно, ждёт подтверждения
   или что-то пошло не так».

Сигнал: SSE-событие → браузерное уведомление (Notification API) + звук
(WebAudio, генерируется на месте — офлайн, без аудиофайлов).

### Д-7. Клиент: один index.html + app.js + style.css

«Один public/index.html + ванильные JS/CSS» читаем как «одна страница без
сборки и CDN»: разметка в `index.html`, стили в `style.css`, логика в
`app.js`. Никаких фреймворков, никаких внешних запросов — всё офлайн.

### Д-8. Безопасность и «только чтение»

- Сервер слушает строго `127.0.0.1`.
- git вызывается только читающими командами фиксированного списка
  (`rev-parse`, `status`, `log`, `diff`, `branch`) через `execFile`
  (не shell) — инъекция через имена файлов невозможна.
- Отдача файлов и `/api/*` проверяют, что запрошенный путь лежит внутри
  проекта (защита от `../`).
- Приложение не пишет ничего в наблюдаемый проект; свои данные держит
  в памяти.

### Д-9. Где живут файлы проекта

Приложение — в каталоге `shturman/` этого репозитория (сайт свадьбы в
`yegor-diana-wedding/` не трогаем). Документы `README.md`, `DECISIONS.md`,
`CHANGELOG.md`, `PROGRESS.md` — внутри `shturman/`.

## Задание 2 (оболочка и телефон)

### Д-18. Конфиг и ярлыки не трогают наблюдаемый проект

`.shturman.json` живёт в домашней папке (`~/.shturman.json`), а не в
проекте: «создаётся сам» не должно нарушать закон «в наблюдаемом проекте
ничего не изменено». Ярлыки Штурман.bat/.command создаются только явной
командой `shturman ярлыки` — это действие пользователя, а не самодеятель-
ность наблюдателя. Для тестов путь конфига подменяется переменной
SHTURMAN_CONFIG.

### Д-19. Модель безопасности share-режима

Слушаем сеть только с флагом --share. Токен — 16 случайных байт hex,
сравнение timing-safe; принимаетcя из ссылки (?t=), cookie или
Authorization: Bearer. Ссылка из QR несёт токен один раз — дальше работает
cookie (SameSite=Lax, сутки). Запросы с loopback — «хозяин»: токен не
нужен, и только хозяину показываются токен и QR (/api/share). Проверка
Host в share-режиме дополнительно пускает IP-литералы, но не домены —
DNS rebinding остаётся закрытым (и без токена чужой домен всё равно
получил бы отказ). Перезапуск сервера = новый токен = отзыв всех ссылок.

### Д-20. PWA честно про http

Service worker и Notification API работают только в «защищённых»
контекстах (https/localhost). На компьютере всё полноценно: установка,
офлайн-страница «Сервер не запущен», уведомления. На телефоне по
локальному http SW не заведётся — сигнал остановки дублируется звуком,
вибрацией и бейджем «🔔» в заголовке, а страница офлайна доступна там,
где SW поддержан. Это ограничение платформы, оно проговорено в FAQ, а не
спрятано.

### Д-21. «Виртуализация» ленты — окно с дозагрузкой

Вместо тяжёлой виртуализации со слежением за высотами — окно из 100
свежих строк и кнопка «Показать ещё (N)»: телефону не приходится держать
сотни DOM-узлов, а редкий заход в глубь истории стоит одного нажатия.
Живые события по-прежнему вставляются инкрементально (rAF-батч из
задания 1). Свёрнутая вкладка через 45 с закрывает SSE-соединение;
возвращение докачивает пропущенное через /events?after=<id> — буфер на
сервере помнит 300 последних событий.

## 2026-07-31 · По ходу разработки

### Д-10. Оценка токенов — только по последней записи usage, помечена «≈»

`usage.input_tokens` + `cache_read` в каждой записи описывают конкретный
запрос, а не сумму. Складывать все input-токены — двойной счёт кеша. Считаем:
сумма `output_tokens` по всем записям + input/cache последней записи как
текущий размер контекста. В интерфейсе всегда со знаком «≈» и подписью
«приблизительно, по данным транскрипта».

### Д-11. Порог «теплового следа» на карте

Подсветка изменённого файла живёт 60 секунд и гаснет плавно (CSS-переход по
данным о времени изменения, пересчёт раз в секунду). Значение выбрано на
глаз: достаточно, чтобы заметить, недостаточно, чтобы вся карта «горела».

### Д-12. SSE-буфер

Кольцевой буфер последних 300 событий; новый клиент получает их пачкой при
подключении (поле `id` растёт монотонно, клиент может передать
`Last-Event-ID`, тогда отдаём только пропущенное). 300 хватает на плотную
сессию, память — копейки.

### Д-13. Служебные состояния — мимо буфера, сигналы — только свежие

Первая живая проверка показала двойное уведомление об остановке. Причина:
периодический «пульс» (раз в 3 с) писался в тот же кольцевой буфер, что и
события ленты, — он и вытеснял реальную историю, и при реплее ломал логику
«не сигналить о том, что случилось до открытия страницы». Решение из двух
половин: (1) у SSE-хаба появился `transient()` — события-состояния (pulse,
git, fs) уходят живым клиентам, но не буферизуются; (2) клиент сигналит
только о `claude-idle` моложе 20 секунд, реплей истории идёт молча.

### Д-14. Стиль кода

Сервер и клиент написаны в едином консервативном стиле (var, function),
без транспиляции и без экзотики — тот же подход, что в остальном
репозитории. Никаких внешних библиотек ни на сервере, ни в браузере.

### Д-15. Итоги адверсарной ревизии (16 исправлений одним заходом)

Прогнал по коду ревизию «пять осей поиска + скептики-верификаторы».
Подтверждённое исправлено:

- **Хвост транскрипта**: остаток недописанной строки был строкой —
  многобайтовый UTF-8 на границе чтения превращался в U+FFFD; теперь
  остаток — Buffer, резка строго по `\n`. Смещения и контексты стали
  per-file: две одновременно активные сессии больше не заставляют tailer
  перечитывать файлы с нуля и заливать ленту дублями; «новая сессия»
  объявляется только для впервые увиденного файла.
- **Разбор записей**: null-элемент в `message.content` ронял процесс —
  добавлены guard-ы.
- **Пульс**: одно сообщение ассистента пишется несколькими записями с
  одинаковым usage — токены считались двойне (дедуп по `message.id`);
  новый запрос человека не сбрасывал прежний `end_turn` — ложный сигнал
  «Клод ждёт» через 5 секунд раздумий; «файлов затронуто» считало один
  файл дважды (абсолютный путь от Edit против относительного от вотчера);
  длительность вчерашней сессии росла всю ночь (теперь до последнего
  события, если тишина дольше порога).
- **Git**: пути с кириллицей приходили восьмеричными escape-ами и ломали
  расшифровку (`-c core.quotepath=false` + свой декодер восьмёрок);
  отсутствие git не распознавалось (err.code='ENOENT' при пустом stderr);
  первый коммит/смена ветки после запуска не давали карточку в ленте.
- **Безопасность**: проверка заголовка Host (DNS rebinding) — принимаем
  только localhost-имена; `/api/file` прогоняет цель через realpath —
  симлинк внутри проекта не выведет чтение наружу; поиск каталога
  транскриптов сверяет `cwd` из JSONL (коллизии кодирования, симлинки
  вида /tmp → /private/tmp на macOS).
- **Клиент**: лента перестала пересобираться на каждое событие (rAF-батч,
  инкрементальная вставка, раскрытые карточки и прокрутка живут при
  потоке событий; реплей 300 событий — без O(N²)); дерево помнит
  раскрытые папки и прокрутку; AudioContext создаётся/будится первым
  жестом пользователя (иначе Chrome молчит); пользовательский порог
  «давно молчит» теперь работает и выше серверных 90 с (одна точка правды
  о сигнале — пульс); подсветка тура работает для целей в sticky-шапке.
- **Вотчер**: событие «сам корень проекта» (Windows отдаёт fileName=null)
  отбрасывается.

### Д-16. Несколько проектов: монитор на папку, метки в SSE

Для бонуса №3 пер-проектная начинка сервера (вотчер, git-опрос, tailer,
пульс, тепловой след) вынесена в `lib/monitor.js` — фабрику
`createMonitor(root, callbacks)`. Сервер держит список мониторов (по
одному на `--project`) и остаётся тонким маршрутизатором: `?project=<id>`
в API, метка `project` в каждом SSE-событии. Идентификатор проекта —
кодированный абсолютный путь (Д-4): стабильный и URL-безопасный. Клиент
фильтрует ленту по метке, панели активного проекта перерисовывает при
переключении, а сигналы остановки обрабатывает для всех проектов сразу
(в уведомлении — имя проекта). Ловушка, найденная при внедрении: монитор
шлёт первые события синхронно из фабрики, поэтому id для колбэков
вычисляется до создания монитора, а не берётся из возвращённого объекта.

### Д-17. Мини-карта внимания — целиком на клиенте

Бонус №4 не потребовал ни одного нового запроса: события ленты уже несут
всё нужное (инструмент + путь файла). Клиент копит след «Клод смотрел на
файл» (Read/Grep — «читал», Edit/Write/… — «правил»), рисует SVG руками
(без библиотек): центр — Клод, лучи — до 8 последних файлов, прозрачность
и размер узла тают за 5 минут. Пути приводятся к относительным по списку
корней проектов; файлы вне проекта на карту не попадают.
