# Сбор данных

## Главный подводный камень: доступ к репозиторию

`list_repos` перечисляет **все** репозитории пользователя — этот вызов работает
всегда. А вот прочитать содержимое репозитория через `mcp__github__*` можно
только если он подключён к текущей сессии. Иначе приходит:

```
Access denied: repository "owner/name" is not configured for this session.
Allowed repositories: owner/other
```

Это не поломка и не повод сдаваться. Порядок действий:

1. Подключи репозиторий: `mcp__claude-code-remote__add_repo` с
   `access: "read"` — для карты достаточно чтения.
2. Повтори чтение.
3. Если подключение не подтвердили — не настаивай и не пытайся обойти. Отметь
   репозиторий в карте как `"unreachable": true` с коротким пояснением. Список,
   дата последнего push и приватность у тебя всё равно есть из `list_repos`, так
   что карточка останется осмысленной, просто без дерева файлов.

Подключение может потребовать подтверждения человека. Если репозиториев много,
запроси доступ ко всем нужным разом в начале, а не по одному в процессе — иначе
человек получит череду отдельных запросов.

## Шаг 1. Список репозиториев

Нужен инструмент, оканчивающийся на `__list_repos`, с `limit: 200`. Отдаёт
`full_name`, `url`, `pushed_at`, `visibility`, `can_push` — этого хватает на
скелет карты, и это одна дешёвая операция.

**Не пиши полное имя инструмента по памяти.** Префикс — это идентификатор
MCP-сервера, и он не постоянный: в одной сессии это может быть
`mcp__claude-code-remote__list_repos`, в другой — `mcp__<uuid>__list_repos`,
причём он способен смениться прямо посреди сессии при переподключении сервера.
Посмотри актуальное имя в списке доступных инструментов и возьми оттуда.

Поиск по ключевым словам здесь ненадёжен: запрос вида `+list_repos` цепляет
`list_repository_collaborators` и прочие похожие имена. Ищи точный суффикс
`__list_repos`.

Если инструмента нет или он требует подтверждения, которое не дали, — карта
строится по репозиториям, уже подключённым к сессии. Обязательно скажи об этом
в ответе. Карта из одного репозитория без пояснения выглядит как «у тебя всего
один репозиторий», а это ровно то заблуждение, от которого скилл должен
избавлять.

Владельца возьми из `mcp__github__get_me` (поле `login`), если он не очевиден из
`full_name`.

## Шаг 2. Дерево файлов

```
mcp__github__get_file_contents(owner, repo, path: "/")
```

Возвращает содержимое директории. Рекурсивно спускайся в поддиректории до
глубины `depth` (по умолчанию 3, считая корень за уровень 1).

**Порядок обхода.** Сначала запроси корень всех репозиториев одной пачкой, потом
следующий уровень — тоже пачкой. Обход «вглубь по одному репозиторию» работает в
разы дольше при том же результате.

### Что пропускать

Эти директории почти никогда не несут смысла в карте и раздувают её:

```
node_modules  .git  dist  build  out  target  vendor  .next  .nuxt
__pycache__  .venv  venv  .pytest_cache  .mypy_cache  coverage
.terraform  Pods  DerivedData  .gradle  .idea  .vscode
```

Директорию из списка показывай как лист без раскрытия — сам факт «здесь есть
node_modules» полезен, её содержимое нет.

Файлы-шум: `*.lock`, `package-lock.json`, `yarn.lock`, `*.min.js`, `*.map`,
`.DS_Store`.

### Ограничения размера

Карта должна оставаться читаемой, поэтому:

- максимум **12 элементов** на директорию;
- максимум **60 узлов** на репозиторий;
- при обрезке добавляй узел-заглушку вида `{"name": "+ ещё 7", "type": "more"}`.

Обрезку показывай явно. Молча урезанное дерево читается как полное, и человек
делает выводы по неполной картине — это ровно та дезориентация, от которой
скилл должен избавлять.

### Приоритет при обрезке

Если элементов больше лимита, оставляй в первую очередь: директории с исходным
кодом (`src`, `app`, `lib`, `assets`), затем конфигурацию и документацию в корне
(`README`, `CLAUDE.md`, `package.json`, `*.config.*`, `.github/`), затем
остальное по алфавиту.

## Шаг 3. Описание репозитория

Прочитай `README.md`, при отсутствии — `CLAUDE.md`, при отсутствии — описание
репозитория из GitHub. Возьми первые осмысленные строки и сожми до **одной
строки в 60–90 символов**: что это за проект и на чём сделан.

Пиши по-человечески, а не копируй заголовок. «Свадебный сайт-приглашение,
статический HTML/CSS/JS без сборки» полезнее, чем «Yegor & Diana».

## Шаг 4. Ветки и открытые PR

```
mcp__github__list_branches(owner, repo, perPage: 30)
mcp__github__list_pull_requests(owner, repo, state: "open", perPage: 10)
```

### Что внутри веток

Само по себе «14 веток без PR» тревожит, но не помогает: непонятно, что там
лежит и что из этого не жалко удалить. Добавь по каждой ветке дату последнего
коммита, его тему и насколько она ушла вперёд от основной.

**Для текущего репозитория бери это из локального git** — быстро, точно, без
запросов и подтверждений:

```bash
git fetch origin --quiet
git rev-list --left-right --count origin/<основная>...origin/<ветка>   # отстаёт / впереди
git log -1 --format='%cs' origin/<ветка>                               # дата
git log -1 --format='%s'  origin/<ветка>                               # тема коммита
```

Тему обрезай примерно до 45 символов — она идёт подписью под именем ветки, а не
пересказом.

**Для остальных репозиториев** доступен только последний коммит — через
`mcp__github__list_commits(owner, repo, sha: "<ветка>", perPage: 1)`. Насколько
ветка ушла вперёд, эти инструменты не считают, и выдумывать число нельзя:
оставь `ahead` пустым.

Сопоставь ветки с PR по полю `head.ref`. Это даёт три полезных состояния для
каждой ветки:

- ветка по умолчанию — база, помечай отдельно;
- ветка с открытым PR — работа в процессе, есть куда вернуться;
- ветка без PR — самый интересный случай: скорее всего именно здесь человек
  остановился и забыл.

## Шаг 5. Незакрытые хвосты

Из уже собранных данных, без дополнительных вызовов:

| Флаг | Условие | Как показывать |
|---|---|---|
| `branch-no-pr` | ветка не default и без открытого PR | «ветка без PR» |
| `stale-pr` | открытый PR не обновлялся > 14 дней | «PR висит N дней» |
| `draft-pr` | PR в статусе draft | «черновик PR» |
| `dormant` | последний push > 90 дней назад | «спит N месяцев» |

Это подсказки, а не приговор. Формулируй нейтрально: «ветка без PR», а не
«заброшено». Часть таких веток намеренно живёт долго, и обвинительный тон в
карте раздражает.

## Схема JSON

Ровно эту структуру подставляй в шаблон вместо `__REPO_MAP_DATA__`:

```json
{
  "owner": "danilandersonai-pixel",
  "generatedAt": "2026-07-28",
  "current": {
    "repo": "Demo",
    "branch": "claude/github-repos-agent-qxj4zi",
    "dirty": 0,
    "note": "всё влито в главную ветку"
  },
  "repos": [
    {
      "name": "Demo",
      "url": "https://github.com/danilandersonai-pixel/Demo",
      "visibility": "public",
      "pushedAt": "2026-07-28",
      "summary": "Свадебный сайт-приглашение, статика без сборки",
      "defaultBranch": "main",
      "unreachable": false,
      "branches": [
        { "name": "main", "isDefault": true, "date": "2026-07-28" },
        {
          "name": "claude/feature-x",
          "isDefault": false,
          "pr": 3,
          "date": "2026-07-13",
          "ahead": 5,
          "behind": 13,
          "subject": "Добавить отдельный переключатель"
        }
      ],
      "pulls": [
        {
          "number": 3,
          "title": "Add feature X",
          "url": "https://github.com/.../pull/3",
          "draft": false,
          "ageDays": 5,
          "branch": "claude/feature-x"
        }
      ],
      "flags": [
        { "kind": "branch-no-pr", "text": "1 ветка без PR" }
      ],
      "tree": [
        { "name": "CLAUDE.md", "type": "file" },
        {
          "name": "assets",
          "type": "dir",
          "children": [{ "name": "css", "type": "dir", "children": [] }]
        }
      ]
    }
  ]
}
```

Поля веток: `date` — дата последнего коммита, `ahead` / `behind` — расхождение с
основной, `subject` — тема последнего коммита. Шаблон сортирует ветки сам:
основная сверху, дальше по свежести. Всё это необязательно — без них ветка
просто покажется одним именем.

Когда карта построена не по свежим данным, а по снимку из
`.claude/repo-map/snapshot.json`, добавь на верхнем уровне `"stale": true` и
`"staleReason"` с одной фразой о причине («список репозиториев требует
подтверждения»). Шаблон нарисует по ним заметную плашку. Без плашки вчерашние
данные читаются как сегодняшние — а это хуже, чем отсутствие карты.

Блок `current` — результат шага 0. Поле `dirty` — число несохранённых файлов,
`note` — короткая приписка о состоянии ветки («отстаёт на 3 коммита», «всё влито
в главную»). Если каталог не git-репозиторий, `current` не добавляй вовсе —
шаблон это переживёт и просто не нарисует панель.

Кроме того, у текущего репозитория ставь `"isCurrent": true`, и у текущей ветки
внутри него — тоже `"isCurrent": true`. По этим двум флагам шаблон рисует
отметки «вы здесь» в древе.

Обязательные поля: `name`, `url`, `visibility`, `pushedAt`. Всё остальное
шаблон переживёт без него — пустое дерево просто не отрисуется, отсутствующий
`summary` не сломает карточку. Это сделано специально, чтобы недоступный
репозиторий всё равно попадал в карту.

Даты — строки `YYYY-MM-DD`. Сортировку по свежести шаблон делает сам.
